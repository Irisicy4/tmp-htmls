Agentic Judge — 3-aspect grounded judging
Page 1 / 3 · Brief design + worked example: task-01 backpack

One agent answer, three independent judges

The LLM-only verifier in EvolveBench v1 reads the agent's prose and assigns a 1–5 score. It cannot tell whether the cited URLs are real, whether the numbers are within the budget, or whether the structured answer actually exists. The agentic judge keeps the LLM rubric and adds two deterministic layers that catch what prose-reading misses.

Brief design

① Hard Constraint Unit Tests

Typed predicates over the agent's structured JSON (price≤$75, count∈[3,5], URL pattern, schema conformance).
Reads only the JSON between === JSON RESULT === delimiters.

② Webpage Grounding sub-agent

Fetches every URL the agent cited. An LLM then reads the rendered pages alongside the agent's answer and decides whether the claim is supported — and can take follow-up questions back from the Effectiveness judge to resolve any pending “is this actually in the source?” doubts.
Reads JSON + live page contents; answers pending checks from ③.

③ Effectiveness judge (LLM)

gpt-4o scores the soft rubric (the original v1 anchors), grounded by the hard + faithfulness reports. When unsure about a citation, it can send a pending question down to ② Webpage Grounding and re-score once the answer comes back.
Reads the full prose + the two reports; may emit pending faithfulness checks.
FINAL COMPOSITION
→
score = clamp(0, 5, llm_overall − 0.5·hard_fails + 0.5·faith_score/5)
pass  = score ≥ 3.0 AND (no hard fails OR llm ≥ 4.0)

Anti-cheat by over-reporting: the schema asks the agent for more fields than the hard layer enforces. The agent does not know which subset is checked, so fabricating just the checked subset costs as much as doing the task — and the faithfulness layer catches URL claims either way.

Worked example — task-01 “backpack under $75”

Output the result as a JSON block between === JSON RESULT === and === END JSON ===.

Required: reference_product.url, options, options[].name, options[].url, options[].price, options[].features, options[].comparison_notes

Optional but rewarded: options[].asin, rating, review_count, …

Step 3 — what each judge concludes

① Hard Constraint Unit Tests

Predicates over the structured JSON only.

  • ✓ summary_schema_conforms — all required fields present
  • ✓ quantity_3_to_5 — len(options)=5
  • ✓ all_prices_under_75_usd — $49.99, $38.99, $59.99, $39.99, $44.99
  • ✓ every_option_has_url — all match https?://
  • ✓ reference_url_present — B09YRC9Y3G
5 / 5 PASS · hard_penalty = 0

② Webpage Grounding sub-agent

Fetched 4 URLs (reference + first 3 options) and looked for the agent's claim in the rendered page text.

  • ✗ B09YRC9Y3G — claim "backpack" not in page
  • ✗ B0BDLH7K67 — claim "Gieury" not in page
  • ✗ B0FDKLS9YY — claim "Sirmaeed" not in page
  • ✓ B01J24H2K0 — claim "Amazon" verified
1 / 4 matched · faith_bonus = +0.12

③ Effectiveness judge (gpt-4o)

Scores the original v1 rubric; reads everything plus the two reports above as grounding.

  • constraint_satisfaction   5/5
  • result_specificity   5/5
  • comparison_quality   5/5
  • task_completeness   5/5
overall 5.0 / 5

Final composition

final = clamp(0, 5, llm_overall − hard_penalty + faith_bonus)
      = clamp(0, 5,    5.0       −     0.0       +    0.12     )
      = 5.0    PASS
⚠ But the faithfulness judge surfaced a real issue the LLM judge missed. Three of the four cited Amazon pages returned HTTP 200, yet the product names the agent attributed to those ASINs are not on those pages. The LLM judge graded the answer 5/5 across the board — the deterministic URL-fetch layer is the only one that flagged the "plausible URL + fabricated stat" failure mode.

Two more examples — which judge catches what, and where it reads

Both runs are from r17 on Modal with codex (ChatGPT subscription). Each answer is shown in compact form, then the per-judge verdict.

task-12 — “Compose an email to David Sullivan”

Instruction: compose an email to dgs@bu.edu offering a one-day Java class on Nov 29 or Nov 30; include a cold-weather caution; do not actually send it.

Agent's structured answer

{
  "recipient":            "dgs@bu.edu",
  "subject":              "One-day basic Java class availability",
  "body":                 "Dear David Sullivan, I am writing to let you
                           know that the one-day basic Java class is
                           available on either November 29 or
                           November 30. Please dress warmly...",
  "dates_mentioned":      ["November 29", "November 30"],
  "includes_cold_warning":true,
  "sent":                 false
}

No URLs ⇒ no faithfulness layer.

What each judge caught

Hard
  • ✓ recipient_correct — equals "dgs@bu.edu"
  • ✓ subject_present   ✓ body_present
  • ✓ not_actually_sent — sent=false
  • ✓ both_dates_offered — Nov 29 AND Nov 30
6 / 6 hard PASS
Effectiveness

gpt-4o reads the prose + JSON. Scores task_completion 5, email_quality 5, completeness 5 ⇒ overall 5.0.

Insight. The LLM judge would have credited any plausibly-formatted email. The hard layer is what enforces the literal facts: the address, the two specific dates, and the “do not send” rule. With only the LLM judge, a model that addressed the wrong recipient or sent the message would still likely score ≥4.

task-43 — “Are Clemenules clementines normally seedless?”

A horticultural question with one verifiable correct answer (yes, they are parthenocarpic) and a known mechanism for occasional seeds (cross-pollination with nearby compatible citrus).

Agent's structured answer

{
  "normally_seedless": true,
  "cross_pollination_explanation":
       "Clemenules are parthenocarpic; bees moving pollen
        from compatible mandarins induce seed formation.",
  "source_url":        "https://agris.fao.org/.../675983...",
  "evidence_quote":    "Isolated flowers of Nules clementine produce
                        seedless fruit; cross-pollination by neighbouring
                        compatible varieties is the main cause of seediness."
}

What each judge caught

Hard
  • ✓ normally_seedless_correct — equals true
  • ✓ has_source_url · source_url_is_http
  • ✓ evidence_quote_substantive — 9-word quote
Faithfulness

Fetched agris.fao.org/... → HTTP 200. The first 6 words of the cited quote (“Isolated flowers of Nules clementine”) appear verbatim in the page text. 1/1 verified.

Effectiveness

⚠ The single LLM judge crashed (returned dimension_scores=None). The Harbor verdict would be 0/5.

Insight. The deterministic layers recovered the verdict when the LLM judge pipeline failed. The hard predicates confirmed the agent gave the right answer; the faithfulness fetch confirmed the citation is real and supports the claim. Reading the two reports together is a stronger pass signal than the LLM judge alone would have produced even if it had succeeded.

How Arpan's 11-task run already does this — and what we can adopt

Source: gpt5-v3-11tasks/ — Arpan's 11-task run of codex (gpt-5) on real_118 with a programmatic-check layer wired inline into each task's test_task.py.

Their approach (inspected from verifier/judge_runs.json)

Arpan's variant wires programmatic checks inside each task's test_task.py. The judge call returns a flat dict of booleans next to the LLM scores. Example, task-01:

"programmatic_checks": {
    "json_present":     true,
    "option_count":     5,
    "option_count_ok":  true,
    "amazon_urls_ok":   true
}

The same shape across the 3 tasks that have any checks at all:

Taskprogrammatic_checks
task-01 backpack json_present, option_count, option_count_ok, amazon_urls_ok
task-12 email json_present, recipient_correct, subject_present, body_present
task-43 clementines json_present, normally_seedless_value, normally_seedless_correct, has_source_url
other 8 of 11 tasks {} (no programmatic checks defined)

Side-by-side comparison

DimensionArpan's 11-taskOurs (agentic_judge/grounded)
Where the checks live Inline inside each test_task.py Separate tests/test_grounded.py next to test_task.py
How checks are declared Ad-hoc Python booleans per task Typed primitives: AllValuesLE, ListLengthInRange, EqualsValue, AllURLsMatch, JSONSchemaConforms, AtLeastOneOf, Custom
Coverage 3 of 11 tasks (29%) 12 of 12 wired tasks (100%)
Per-check output Just a boolean (passed, detail) — the failing case explains which item failed and why
Score integration Reported but does not change overall_score Explicit penalty: −0.5 per failed hard check, capped at −2.0
URL verification None Faithfulness layer: fetches every cited URL, verifies claim substring/regex appears in rendered page text
Anti-cheat schema None — agent freely structures its own JSON SUMMARY_SCHEMA declares required + optional fields; agent emits more than is checked
Harbor verifier-output compatibility Yes — the programmatic_checks key already flows through harbor's analysis tooling Currently emits hard_report as a list in our runner's return; not indexed by harbor's dashboards

What we can borrow from them

  1. Emit a flat programmatic_checks dict for harbor compatibility. Our framework/runner.py currently returns hard_report: […] as a list. Adding a five-line shim that also produces {check_name: bool} next to it lets the existing harbor rejudge / agreement / dashboard tooling pick our checks up without any of their code knowing about our framework.
  2. The “factual-answer” assertion pattern. Their normally_seedless_correct: true is the right pattern for tasks that have one objectively verifiable answer. We already have EqualsValue as a primitive but had not consistently used it for the “key factual claim” on each task. Sweep the cohort for tasks with a single-fact answer and add an EqualsValue(<answer-field>, <known-correct>) assertion.
  3. For trivial tasks, an inline check inside test_task.py is lighter than a full test_grounded.py. Our split makes sense when there are several predicates plus faithfulness checks. For a task with two booleans and no URLs (e.g. task-43 in their version), their inline approach is simpler. We can keep our split as the default and accept inline checks as a valid light-touch alternative for the long tail.
  4. Their judge prompt explicitly mentions the programmatic-check verdict in the LLM call. We do this too (effectiveness.py includes the hard report in the prompt), but theirs has a one-line natural-language summary of which boolean failed. Adopting that one-line summary makes the LLM's grounding more visible in dimension_reasoning.

Net

Arpan's implementation validates that programmatic checks alongside an LLM judge improve verdict quality and reproducibility. Our framework generalises that idea — typed primitives, separated spec file, URL-fetch faithfulness layer, anti-cheat schema, score integration — but we should adopt his flat-dict output format so we plug into harbor's existing analysis pipeline rather than running parallel to it.
