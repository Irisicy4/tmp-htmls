# Experiment 1: Deprivacy-100 Cross-Agent Benchmark

Run all 100 tasks from `tasks/updated-deprivacy-100` across every supported agent, then compare results.

## What this covers

- **100 tasks** across 13 categories: Shopping (15), Daily Activities (25), Travel & Planning (11), Software Engineering (11), Finance & Economics (10), Marketing & Analytics (8), Data & ML Engineering (7), (Self) Media (7), HR & Recruiting (2), Design (2), Medical (1), General (1)
- **4 agents**: claude-code, codex, gemini-cli, aider
- **LLM-as-judge evaluation**: Each task has a custom rubric with 3-5 scoring dimensions (1-5 scale), majority voting for borderline cases
- **Cross-agent analysis**: head-to-head comparison, per-category breakdown, per-dimension averages

## Quick start

```bash
cd evolve_bench_harbor

# 1. Deploy the Modal app (one time)
modal deploy scripts_batch/deprivacy_modal_runner.py

# 2. Smoke test (3 tasks, one agent)
python scripts_batch/trigger_deprivacy.py --agent claude-code --first-n 3

# 3. Full run — all agents, all 100 tasks
bash scripts_batch/run_all_agents.sh

# 4. Collect results (after experiments finish)
modal run scripts_batch/deprivacy_modal_runner.py --list-runs
modal run scripts_batch/deprivacy_modal_runner.py --collect deprivacy/claude-code/<timestamp>
modal run scripts_batch/deprivacy_modal_runner.py --collect deprivacy/codex/<timestamp>
modal run scripts_batch/deprivacy_modal_runner.py --collect deprivacy/gemini-cli/<timestamp>
modal run scripts_batch/deprivacy_modal_runner.py --collect deprivacy/aider/<timestamp>

# 5. Cross-agent analysis
python scripts_batch/analyze_cross_agent.py results/deprivacy/
```

## Files

| File | Purpose |
|------|---------|
| `deprivacy_modal_runner.py` | Modal app — bakes in deprivacy-100 tasks, runs agent, evaluates, saves enriched results |
| `trigger_deprivacy.py` | Fire-and-forget trigger for a single agent run |
| `run_all_agents.sh` | Trigger all 4 agents in sequence (each runs in parallel on Modal) |
| `analyze_cross_agent.py` | Post-hoc analysis: comparison tables, CSV matrix, JSON summary |

## Improvements over original output structure

The original `harbor_modal_runner.py` result format has several gaps that make cross-agent analysis painful. Here's what this experiment fixes:

### Problem 1: No agent/model identity in per-task results

**Original:** Each task result only has `task`, `score`, `passed`, `feedback`. If you collect results from multiple agents into the same directory, you can't tell which result came from which agent without relying on the directory path.

**Fix:** Every result now includes `agent`, `model`, `run_tag` at the top level. Results are self-describing — you can `cat *.json | jq` and group by agent without knowing the directory structure.

### Problem 2: No task metadata (category, tags) in results

**Original:** Category and tags live only in `task.toml` inside the task definition. To analyze "how did agents do on Shopping tasks vs Software Engineering tasks?", you'd need to join results with task.toml files manually.

**Fix:** `category` and `tags` from `task.toml` are baked into every result JSON. The summary includes a full `category_summary` breakdown. No post-hoc joining needed.

### Problem 3: Dimension scores buried inside nested `eval.details`

**Original:** The per-dimension rubric scores (e.g., `constraint_satisfaction: 5`) are nested inside `eval.details.dimension_scores`. This makes aggregation awkward — you need to dig two levels deep and handle missing keys.

**Fix:** `dimension_scores` is flattened to the top level of each result. The summary includes `dimension_averages` — the mean of each dimension across all tasks. You can instantly see "agents are weak on comparison_quality (2.8 avg) but strong on constraint_satisfaction (3.9)".

### Problem 4: No timestamps or timing data

**Original:** No way to know how long each task took, when it ran, or whether slow tasks correlate with low scores.

**Fix:** Every result has `started_at` and `finished_at` (ISO 8601). The orchestrator logs per-task elapsed time. You can identify tasks that consistently time out or take 10x longer than others.

### Problem 5: No structured cross-agent comparison format

**Original:** Each agent run produces its own `summary.json` with just the flat stats. Comparing agents means manually opening multiple files, aligning task names, and computing deltas by hand.

**Fix:** `analyze_cross_agent.py` produces:
- `cross_agent_summary.json` — all agents in one file, with a task-level score matrix
- `per_task_matrix.csv` — ready for Excel/Sheets pivot tables, pandas heatmaps, or any visualization tool
- Console output with head-to-head win/loss/tie counts

### Problem 6: No error count in summary

**Original:** Summary only has `n_tasks` and `n_passed`. If 10 tasks errored (sandbox crash, timeout), they're silently mixed into "not passed" with no way to distinguish "agent tried and failed" from "infrastructure broke".

**Fix:** `n_errors` is tracked separately. A task with `"error": "Sandbox did not become ready"` is clearly infrastructure, not agent quality.

### Problem 7: Evidence and reasoning not surfaced

**Original:** The LLM judge produces detailed `evidence_summary` and `dimension_reasoning` but these are buried inside `eval.details` and not easily searchable.

**Fix:** Both are surfaced to the top level of each result. You can grep across all results for specific reasoning patterns (e.g., `grep -r "exceeded.*budget" results/` to find all budget violations across agents).
