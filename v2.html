Agentic Judge v2
Page 1 / 3

Effectiveness is the main judge — and it can call Faithfulness

The LLM-only verifier in EvolveBench v1 reads the agent's prose and assigns a 1–5 score. It cannot tell whether the cited URLs are real, whether the numbers are within the budget, or whether the structured answer actually exists. The agentic judge keeps the LLM rubric, adds a deterministic Hard layer for typed predicates, and gives the LLM judge an agentic Faithfulness sub-agent it can dispatch to verify any cited URL — including the agent's “I couldn't find X” claims.

Brief design

① Hard Constraint judge

Typed predicates over the agent's structured JSON (price≤$75, count∈[3,5], URL pattern, schema conformance).
Reads only the JSON between === JSON RESULT === delimiters.

② Faithfulness sub-agent (LLM)

On request, fetches a URL and uses an LLM to read the rendered page and answer either: (a) does this page support a specific claim the agent made? or (b) a natural-language question from the main judge — including the most common one, “is the agent's ‘I couldn't find X’ actually true on this source?”
Reads live page contents; returns {supported, evidence_quote, answer, reasoning}.

③ Effectiveness — the main judge (LLM)

gpt-4o scores the soft rubric grounded by the hard report and an initial faithfulness sweep. If it is unsure whether a citation supports a claim, OR if it wants to verify the agent's unanswerability claims, it emits pending_faith_questions: [{url, question}]. The runner dispatches each through ②, then re-calls ③ with the answers so it can revise its dimension scores.
Reads full prose + JSON + Hard report + initial Faith report; emits pending faith questions and re-scores.
FINAL COMPOSITION
→
score = clamp(0, 5, llm_overall − 0.5·hard_fails + 0.5·faith_score/5)
pass  = score ≥ 3.0 AND (no hard fails OR llm ≥ 4.0)

Anti-cheat by over-reporting: the schema asks the agent for more fields than the hard layer enforces. The agent does not know which subset is checked, so fabricating just the checked subset costs as much as doing the task — and the faithfulness sub-agent catches both fabricated citations and false unanswerability claims.

Flow — five nodes, one feedback loop

Five nodes, one loop. ② Faithfulness is a single sub-agent — its first call produces the initial faith_report; subsequent calls answer pending_faith_questions from ③. The dashed purple arc is the agentic step.

Step 3 — what each judge does (job + its prompt)

① Hard Constraint judge

Job. Run a list of typed Python predicates against the agent's structured JSON. No LLM call. Each predicate returns (passed, detail).

Predicate list (task-01)

HARD_CONSTRAINTS = [
  JSONSchemaConforms(required_paths=SUMMARY_SCHEMA.required_paths()),
  ListLengthInRange("options", 3, 5,         name="quantity_3_to_5"),
  AllValuesLE       ("options.*.price", 75,  name="all_prices_under_75_usd"),
  AllURLsMatch      ("options.*.url",
                      r"^https?://",          name="every_option_has_url"),
  FieldPresent      ("reference_product.url", name="reference_url_present"),
]

② Faithfulness sub-agent

Job. Fetch each URL the agent cited, hand the rendered page to an LLM, and return a verdict on whether the page actually supports the claim — and answer any follow-up question from ③.

System prompt (trimmed)

You are a precise source-checking sub-agent.  You are given:
  - the rendered text of a web page the agent cited as evidence,
  - the agent's specific claim about that page,
  - (optionally) a follow-up question from the Effectiveness judge.
Decide whether the page actually supports the claim, and answer the
question if one is given.  Paraphrases count; numeric values must be
within plausible rounding; off-topic / paywalled ⇒ unsupported.

Return ONLY:
{ "supported": true|false,
  "evidence_quote": "",
  "answer": "",
  "reasoning": "" }

③ Effectiveness — main judge

Job. Score each soft-rubric dimension 1–5, grounded by the Hard and Faithfulness reports. Owns the final verdict. May dispatch follow-up questions to ② and re-score once the answers come back.

System prompt (trimmed)

You are the MAIN evaluator scoring an AI agent's work.  You are given:
  1. agent's structured summary JSON,
  2. a hard-constraint report,
  3. a faithfulness report (URL fetches + claim verification).

You are also AGENTIC: when uncertain about whether a cited URL supports
a claim — OR when the agent says "I could not find X" and you want to
verify that — emit `pending_faith_questions`.  A Faithfulness sub-agent
will fetch each URL and answer.  We will then call you a second time
with the answers so you can revise your scores.  Cap: 3 questions/task.

Score honestly.  A FAILED hard constraint or failed faithfulness check
caps the relevant dimension below 5.

Two more examples — which judge catches what, and where it reads

Both runs are from r18 on Modal with codex (ChatGPT subscription) using v2 (LLM-agentic Faithfulness + pending-question loop). Each answer is shown in compact form, then the per-judge verdict.

task-12 — “Compose an email to David Sullivan”

Instruction: compose an email to dgs@bu.edu offering a one-day Java class on Nov 29 or Nov 30; include a cold-weather caution; do not actually send it.

Agent's structured answer

{
  "recipient":            "dgs@bu.edu",
  "subject":              "One-day basic Java class availability",
  "body":                 "Dear David Sullivan, I am writing to let you
                           know that the one-day basic Java class is
                           available on either November 29 or
                           November 30. Please dress warmly...",
  "dates_mentioned":      ["November 29", "November 30"],
  "includes_cold_warning":true,
  "sent":                 false
}

No URLs ⇒ no faithfulness layer.

What each judge caught

Hard
  • ✓ recipient_correct — equals "dgs@bu.edu"
  • ✓ subject_present   ✓ body_present
  • ✓ not_actually_sent — sent=false
  • ✓ both_dates_offered — Nov 29 AND Nov 30
6 / 6 hard PASS
Effectiveness

gpt-4o reads the prose + JSON. Scores task_completion 5, email_quality 5, completeness 5 ⇒ overall 5.0.

Insight. The LLM judge would have credited any plausibly-formatted email. The hard layer is what enforces the literal facts: the address, the two specific dates, and the “do not send” rule. With only the LLM judge, a model that addressed the wrong recipient or sent the message would still likely score ≥4.

task-43 — “Are Clemenules clementines normally seedless?”

A horticultural question with one verifiable correct answer (yes, they are parthenocarpic) and a known mechanism for occasional seeds (cross-pollination with nearby compatible citrus).

Agent's structured answer

{
  "normally_seedless": true,
  "cross_pollination_explanation":
       "Clemenules are parthenocarpic; bees moving pollen
        from compatible mandarins induce seed formation.",
  "source_url":        "https://agris.fao.org/.../675983...",
  "evidence_quote":    "Isolated flowers of Nules clementine produce
                        seedless fruit; cross-pollination by neighbouring
                        compatible varieties is the main cause of seediness."
}

What each judge caught

Hard
  • ✓ normally_seedless_correct — equals true
  • ✓ has_source_url · source_url_is_http
  • ✓ evidence_quote_substantive — 9-word quote
Faithfulness sub-agent

Fetched agris.fao.org/... → HTTP 200. LLM verdict: supported=true, evidence_quote: “Isolated flowers of Nules clementine produce seedless fruit; cross-pollination by neighbouring compatible varieties is the main cause of seediness.”

Effectiveness (main judge)

First pass scored 5/5, then raised one pending question to the Faithfulness sub-agent: “The agent says ‘no peer-reviewed paper after 2018 disagrees’ — verify this on the FAO listing.” Sub-agent replied supported=true. No revision needed. Overall 5.0.

Insight. Even when the first pass would have passed by itself, the main judge actively verified the agent's negative claim ("no later paper disagrees") through the Faithfulness sub-agent rather than trusting prose. The agentic loop catches false unanswerability claims that single-pass judges miss.

How Arpan's 11-task run already does this — and what we can adopt

Source: gpt5-v3-11tasks/ — Arpan's 11-task run of codex (gpt-5) on real_118 with a programmatic-check layer wired inline into each task's test_task.py.

Their approach (inspected from verifier/judge_runs.json)

Arpan's variant wires programmatic checks inside each task's test_task.py. The judge call returns a flat dict of booleans next to the LLM scores. Example, task-01:

"programmatic_checks": {
    "json_present":     true,
    "option_count":     5,
    "option_count_ok":  true,
    "amazon_urls_ok":   true
}

The same shape across the 3 tasks that have any checks at all:

Taskprogrammatic_checks
task-01 backpack json_present, option_count, option_count_ok, amazon_urls_ok
task-12 email json_present, recipient_correct, subject_present, body_present
task-43 clementines json_present, normally_seedless_value, normally_seedless_correct, has_source_url
other 8 of 11 tasks {} (no programmatic checks defined)

What we can borrow from them

  1. Emit a flat programmatic_checks dict for harbor compatibility. Our framework/runner.py currently returns hard_report: […] as a list. Adding a five-line shim that also produces {check_name: bool} next to it lets the existing harbor rejudge / agreement / dashboard tooling pick our checks up without any of their code knowing about our framework.
  2. The “factual-answer” assertion pattern. Their normally_seedless_correct: true is the right pattern for tasks that have one objectively verifiable answer. We already have EqualsValue as a primitive but had not consistently used it for the “key factual claim” on each task. Sweep the cohort for tasks with a single-fact answer and add an EqualsValue(<answer-field>, <known-correct>) assertion.
  3. For trivial tasks, an inline check inside test_task.py is lighter than a full test_grounded.py. Our split makes sense when there are several predicates plus faithfulness checks. For a task with two booleans and no URLs (e.g. task-43 in their version), their inline approach is simpler. We can keep our split as the default and accept inline checks as a valid light-touch alternative for the long tail.
  4. Their judge prompt explicitly mentions the programmatic-check verdict in the LLM call. We do this too (effectiveness.py includes the hard report in the prompt), but theirs has a one-line natural-language summary of which boolean failed. Adopting that one-line summary makes the LLM's grounding more visible in dimension_reasoning.

Net

Arpan's implementation validates that programmatic checks alongside an LLM judge improve verdict quality and reproducibility. v2 generalises that idea further: typed Hard predicates, an LLM-agentic Faithfulness sub-agent that handles paraphrase and natural-language questions, and a main judge that can call it mid-judgment to verify both citations and unanswerability claims. We still adopt Arpan's flat-dict output format so v2 plugs into harbor's existing analysis pipeline rather than running parallel to it.
