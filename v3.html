How the agentic judge works

A single language model reading the agent's prose and assigning a score can be fooled by an answer that looks well-cited but isn't. The agentic judge keeps the rubric scoring, adds a small layer of structural checks for the things that have one right answer, and gives the main judge a source-checking helper it can ask to actually open the cited pages and verify what the agent said.

The three judges

① Structural checks

A handful of simple checks for the things that have one right answer per task — was the budget respected, was the schema filled in, does each cited URL look like a URL. No language model involved.

② Source-checking helper

For each page the agent cited, it fetches the page and asks a language model whether the page really supports what the agent said. It can also answer follow-ups from the main judge — for example, "the agent claimed this source doesn't mention X; is that actually true?"

③ The main judge

One model reads everything — the agent's answer, the structural and source-checking results, and the agent's full work trace including pages it visited but never wrote down. It scores the rubric, sends follow-up questions to the source helper when something looks off, then revises its scores when the answers come back.

The three results compose into a single score and a pass/fail. Structural failures pull the score down; verified citations nudge it up. The arithmetic is intentionally simple so the verdict is easy to audit — anyone can replay any of the three layers on its own.

Flow — five nodes, one feedback loop

The structural and source-checking results feed into the main judge. When the main judge isn't sure about a citation, it sends a follow-up question back to the source helper (the dashed purple arrow), waits for the answer, then revises its scores. The verdict it ships is always the revised one.

Worked example — a shopping research task

Step 1 — what we sent to the agent

Original task

"I'm looking for a backpack under $75 that has all the features of this product. Please do some research and find three to five options and summarize their key features and prices, comparing them to the original."

What we added to the task

We asked the agent to also produce a structured summary at the end — one block listing each option with its name, URL, price, features, and a short note comparing it to the original.

We told the agent that the grader would fetch each URL and verify the figures and quotes against the live page, so it should be precise.

Step 2 — what the agent wrote (short excerpt)

The agent produced a few paragraphs of reasoning and then a structured summary listing five backpacks:

  • Gieury Anti-Theft Laptop Backpack · $49.99 · USB port, TSA-friendly
  • Sirmaeed 35L Carry-on · $38.99 · expandable, luggage strap
  • Amazon Basics Travel Backpack · $59.99 · 40L, convertible
  • MATEIN 40L Carry-on · $39.99
  • VANKEAN 17.3-inch Laptop Backpack · $44.99

Each option carries a real Amazon product URL the agent cited as its source.

Coloured underlines mark where each judge looks. Blue is for the structural checks, amber for the source-checking helper (the URLs it fetched), and the main judge reads everything in scope.

Step 3 — what each judge does

① Structural checks

A small list of programmatic checks on the agent's structured answer — the kinds of things that have one right answer per task: did the agent put a recipient in the recipient slot, are all five prices under the budget, did the schema get filled in, does the cited URL look like a URL. No language model is involved. Each check passes or fails with a short reason.

Example check list (for the shopping task above)

CHECKS = [
  schema_filled_in,
  options_count_between_3_and_5,
  every_price_under_75,
  every_option_has_a_url,
  reference_product_url_present,
]

② Source-checking helper

For every page the agent cited, this helper fetches the page and asks a language model: does this page actually back up what the agent said about it? If yes, it returns a short quote from the page as evidence; if no, it explains why. It can also answer follow-up questions from the main judge — for example, "the agent said this source doesn't mention X; can you confirm that on the page?"

What this helper is told

You are a precise source-checking helper.  You are given:
  - the rendered text of a web page the agent cited as evidence,
  - the agent's specific claim about that page,
  - (optional) a follow-up question from the main judge.

Decide whether the page actually supports the claim, and answer
the follow-up if there is one.  Paraphrases count; numeric values
must be within plausible rounding; if the page is empty, blocked,
or off-topic, mark unsupported.

Reply with:
  supported       : yes / no
  evidence_quote  : a short verbatim snippet from the page
  answer          : your answer to the follow-up (if any)
  reasoning       : one short sentence

③ The main judge

One model reads the whole picture: the agent's answer, its structured summary, the results of the structural checks, the source-checking results, and the agent's full work trace (every tool call, every page it actually visited, including dead ends and pages it never wrote down). It scores each rubric dimension and writes a short justification.

When something doesn't add up — a citation that looks fishy, a "couldn't find it" claim worth double-checking, a source the agent visited but never quoted — the main judge sends a follow-up question back to the source-checking helper, waits for the answer, and then revises its scores. The verdict it ships is always the revised one.

The judge inherits whatever rubric the task already came with — the same dimension names, weights, and what-counts-as-a-5 language that the original task used. That means it's not inventing standards; it's just scoring against the existing ones with more grounding to lean on.

What this judge is told

You are the main evaluator scoring an AI agent's work.  You have
four pieces of evidence:
  1. the agent's structured summary,
  2. the structural-check results,
  3. the source-checking results for the URLs in the summary,
  4. the agent's full work trace — every tool call, every page it
     opened to verify something, every dead end.

Read the trace carefully.  Agents often visit pages they never put
in their final summary; those pages are still load-bearing for
your verdict.

If you are uncertain about whether a cited page supports a claim,
or if the agent says "I couldn't find X" and you want to verify
that, send a follow-up question to the source-checking helper.
The helper will fetch the page and reply; you will then re-score
with the new evidence.  Cap: 3 follow-ups per task.

You must send a follow-up in these cases:
  - The source-checking helper says a claim is unsupported but you
    suspect a paraphrase was missed.
  - The agent's trace shows a URL that the helper has not yet
    verified and the answer would change a score.

Score honestly.  Structural checks check shape — not semantic
quality.  An option priced $74.99 satisfies the budget cap even
if its features have nothing to do with what the user asked for.
A perfect structural pass does not automatically mean a perfect
soft-rubric score; read the agent's reasoning before assigning a
five.

Plus: the rubric from the original task

The judge inherits the task's existing rubric — the dimension names, weights, and what-counts-as-a-5 anchor language — directly from the task definition. For the shopping example, the judge is given:

Dimensions to score (1 to 5):
  - constraint_satisfaction (weight 0.30)
  - result_specificity      (weight 0.25)
  - comparison_quality      (weight 0.25)
  - task_completeness       (weight 0.20)

Anchor language:
  constraint_satisfaction
    1 = budget cap ignored
    3 = some items over budget
    5 = every option within budget AND every feature of the
        reference covered
  result_specificity
    1 = generic suggestions
    3 = brand and model named
    5 = exact product code, price, and URL per item
  comparison_quality
    1 = list only, no comparison
    3 = a couple of features compared
    5 = each option mapped back to each of the reference's features
  task_completeness
    1 = fewer than 3 options returned
    3 = 3 or 4 options
    5 = 3 to 5 options with a full feature sweep

Step 4 — what the judge concluded on this answer

All five structural checks passed (the agent gave five options, every price was under the budget, every URL was well-formed, the schema was complete). The source-checking helper visited the four cited Amazon pages and found that three of them did not actually contain the brand the agent had attributed to that product — the URLs were real, but they didn't lead to the products the agent named.

The main judge read the agent's full work trace alongside this and concluded that the answer was structurally fine and the comparison was thoughtful, but the specificity and completeness dimensions couldn't be a perfect 5 — the cited evidence wasn't holding up. The final score landed in the passing range, but lower than the rubric judge alone would have given it: a more honest reflection of what the agent actually delivered.

What it does well, what it misses, what it gets wrong

What it does well

  • Catches plausible-looking citations that don't actually back the claim.
  • Still produces a verdict if the rubric grader fails — the other two layers carry it.
  • Doesn't invent failure on easy answers with no URLs to verify.
  • Reads the agent's full work trace, not just its final write-up.
  • The three layers stay separate in the output, so any one can be replayed for audit.

Concrete cases where it caught a real problem

TaskWhat the judge caught
Backpack searchThree of four cited Amazon pages didn't actually contain the products the agent named.
Clementines questionRubric grader returned nothing; the other layers verified the cited source and produced a passing verdict on their own.
2025 calendarThree of four cited pages verified; the one empty page was flagged and the source-navigation score lowered.
Camera shoppingStructural checks all passed, but cited Amazon pages came back empty — the judge lowered specificity instead of awarding a perfect rubric.
SEC EDGAR lookupAgent skipped the required structured block; the structural check failed first, so the verdict reflected the schema miss rather than the answer's quality.

What it still misses

IssueWhat happens and what we'd add
Shape passes but the reasoning is wrong An option priced $74.99 satisfies the budget rule even if its features have nothing to do with what the user asked for. Fix: more semantic checks where there's a single objective truth, and lean harder on the rubric judge's reading of the agent's trace.
An infrastructure error looks like a bad answer When the agent's environment crashes or auth breaks, the verdict is just a low score with no signal of why. Fix: a separate infrastructure-error flag, distinct from the score.

Where the judge is too harsh

IssueWhat happens and what we'd add
Anti-bot pages render empty for our fetcher The source-checking helper gets a near-empty page and reports the citation as unsupported, even when the agent saw a real product in its browser. Fix: distinguish "page blocked or empty" from "page renders but doesn't support the claim," and ignore the former.

Two more examples — which judge catches what, and where it reads

Both runs are from r18 on Modal with codex (ChatGPT subscription) using v2 (LLM-agentic Webpage Grounding + pending-question loop). Each answer is shown in compact form, then the per-judge verdict.

task-12 — “Compose an email to David Sullivan”

Instruction: compose an email to dgs@bu.edu offering a one-day Java class on Nov 29 or Nov 30; include a cold-weather caution; do not actually send it.

Agent's structured answer

{
  "recipient":            "dgs@bu.edu",
  "subject":              "One-day basic Java class availability",
  "body":                 "Dear David Sullivan, I am writing to let you
                           know that the one-day basic Java class is
                           available on either November 29 or
                           November 30. Please dress warmly...",
  "dates_mentioned":      ["November 29", "November 30"],
  "includes_cold_warning":true,
  "sent":                 false
}

No URLs ⇒ no faithfulness layer.

What each judge caught

Hard
  • ✓ recipient_correct — equals "dgs@bu.edu"
  • ✓ subject_present   ✓ body_present
  • ✓ not_actually_sent — sent=false
  • ✓ both_dates_offered — Nov 29 AND Nov 30
6 / 6 hard PASS
Effectiveness

gpt-4o reads the prose + JSON. Scores task_completion 5, email_quality 5, completeness 5 ⇒ overall 5.0.

Insight. The LLM judge would have credited any plausibly-formatted email. The hard layer is what enforces the literal facts: the address, the two specific dates, and the “do not send” rule. With only the LLM judge, a model that addressed the wrong recipient or sent the message would still likely score ≥4.

task-43 — “Are Clemenules clementines normally seedless?”

A horticultural question with one verifiable correct answer (yes, they are parthenocarpic) and a known mechanism for occasional seeds (cross-pollination with nearby compatible citrus).

Agent's structured answer

{
  "normally_seedless": true,
  "cross_pollination_explanation":
       "Clemenules are parthenocarpic; bees moving pollen
        from compatible mandarins induce seed formation.",
  "source_url":        "https://agris.fao.org/.../675983...",
  "evidence_quote":    "Isolated flowers of Nules clementine produce
                        seedless fruit; cross-pollination by neighbouring
                        compatible varieties is the main cause of seediness."
}

What each judge caught

Hard
  • ✓ normally_seedless_correct — equals true
  • ✓ has_source_url · source_url_is_http
  • ✓ evidence_quote_substantive — 9-word quote
Webpage Grounding sub-agent

Fetched agris.fao.org/... → HTTP 200. LLM verdict: supported=true, evidence_quote: “Isolated flowers of Nules clementine produce seedless fruit; cross-pollination by neighbouring compatible varieties is the main cause of seediness.”

Effectiveness (main judge)

First pass scored 5/5, then raised one pending question to the Webpage Grounding sub-agent: “The agent says ‘no peer-reviewed paper after 2018 disagrees’ — verify this on the FAO listing.” Sub-agent replied supported=true. No revision needed. Overall 5.0.

Insight. Even when the first pass would have passed by itself, the main judge actively verified the agent's negative claim ("no later paper disagrees") through the Webpage Grounding sub-agent rather than trusting prose. The agentic loop catches false unanswerability claims that single-pass judges miss.

How Arpan's 11-task run already does this — and what we can adopt

Source: gpt5-v3-11tasks/ — Arpan's 11-task run of codex (gpt-5) on real_118 with a programmatic-check layer wired inline into each task's test_task.py.

Their approach (inspected from verifier/judge_runs.json)

Arpan's variant wires programmatic checks inside each task's test_task.py. The judge call returns a flat dict of booleans next to the LLM scores. Example, task-01:

"programmatic_checks": {
    "json_present":     true,
    "option_count":     5,
    "option_count_ok":  true,
    "amazon_urls_ok":   true
}

The same shape across the 3 tasks that have any checks at all:

Taskprogrammatic_checks
task-01 backpack json_present, option_count, option_count_ok, amazon_urls_ok
task-12 email json_present, recipient_correct, subject_present, body_present
task-43 clementines json_present, normally_seedless_value, normally_seedless_correct, has_source_url
other 8 of 11 tasks {} (no programmatic checks defined)

What we can borrow from them

  1. Emit a flat programmatic_checks dict for harbor compatibility. Our framework/runner.py currently returns hard_report: […] as a list. Adding a five-line shim that also produces {check_name: bool} next to it lets the existing harbor rejudge / agreement / dashboard tooling pick our checks up without any of their code knowing about our framework.
  2. The “factual-answer” assertion pattern. Their normally_seedless_correct: true is the right pattern for tasks that have one objectively verifiable answer. We already have EqualsValue as a primitive but had not consistently used it for the “key factual claim” on each task. Sweep the cohort for tasks with a single-fact answer and add an EqualsValue(<answer-field>, <known-correct>) assertion.
  3. For trivial tasks, an inline check inside test_task.py is lighter than a full test_grounded.py. Our split makes sense when there are several predicates plus faithfulness checks. For a task with two booleans and no URLs (e.g. task-43 in their version), their inline approach is simpler. We can keep our split as the default and accept inline checks as a valid light-touch alternative for the long tail.
  4. Their judge prompt explicitly mentions the programmatic-check verdict in the LLM call. We do this too (effectiveness.py includes the hard report in the prompt), but theirs has a one-line natural-language summary of which boolean failed. Adopting that one-line summary makes the LLM's grounding more visible in dimension_reasoning.

Net

Arpan's implementation validates that programmatic checks alongside an LLM judge improve verdict quality and reproducibility. v2 generalises that idea further: typed Hard predicates, an LLM-agentic Webpage Grounding sub-agent that handles paraphrase and natural-language questions, and a main judge that can call it mid-judgment to verify both citations and unanswerability claims. We still adopt Arpan's flat-dict output format so v2 plugs into harbor's existing analysis pipeline rather than running parallel to it.
